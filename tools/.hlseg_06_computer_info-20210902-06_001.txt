001、程式被閱讀的次數遠超過撰寫，每次讓下一個讀者少花一秒，後續修改成本就下降。
002、乾淨程式的操作定義是每個常式讀完都幾乎符合預期，沒有隱藏副作用或突兀細節。
003、稍後再整理等於永遠不整理，髒碼必須在碰觸當下縮小，不能排進假設的清潔時段。
004、每次簽入都該讓營地比進來時更乾淨，即使只是把一個誤導名稱改成意圖名稱。
005、一扇破窗會讓下一手更隨意；模組一旦混亂，後續修改會複製並放大該混亂。
006、名稱必須揭示意圖，讀識別字就該知道為何存在、做什麼、如何用，不必先翻本體。
007、錯誤資訊比含糊更危險，把 hp 或 aix 當區域變數會讓人聯想到完全不相干的系統。
008、Meaningful distinction 禁止 Product 與 ProductInfo 這種只靠後綴、語意重疊的成對命名。
009、名稱必須能唸出來，團隊才能在口頭設計討論中引用，而不是指著螢幕拼字母。
010、可搜尋性要求具意義的字要夠長、魔術數字要具名，讓全專案搜尋不會淹沒在雜訊裡。
011、Hungarian 與 m_ 前綴在有型別系統與重構工具的語言裡是過時編碼，會把型別謊言寫進名字。
012、同一概念全專案只用一個詞；get、fetch、retrieve 混用會讓呼叫端無法建立穩定詞彙表。
013、雙關會把 add 同時當成長度相加與集合插入，呼叫端無法從名字判斷契約。
014、解題域詞彙用在演算法與模式細節層，問題域詞彙用在業務規則層，兩層詞庫不可對調。
015、上下文前綴只加到能消歧義為止；每個類都冠上應用名稱是多餘上下文，會遮住真正差異。
016、類名用名詞片語、方法名用動詞片語，俏皮暱稱與內部笑話在專業程式裡沒有位置。
017、函式必須極短，二十行已偏長，長度的上限是它仍然只做一件能用一句話命名的事。
018、函式的一件事以同一抽象層級與同一個變更理由判定，不是靠行數少來宣稱合格。
019、Stepdown Rule 讓檔案由上而下從政策走到細節，高階函式只陳述做什麼，低階才回答怎麼做。
020、單一函式不得混兩個抽象層級，迴圈裡的細節步驟應抽成與高階敘事對齊的具名操作。
021、switch 的重複 case 應收斂到一處工廠，用多型新增型別，而不是把同一組分支複製到各處。
022、引數以零個為理想、一個常見、兩個需謹慎，三個以上幾乎總該收成參數物件。
023、布林旗標引數把兩個執行路徑塞進同一簽章，應拆成兩個意圖明確的方法。
024、輸出引數違反參數是輸入的閱讀慣例，改由回傳值或接收者自身狀態表達結果。
025、Command Query Separation 禁止方法既改變狀態又當布林判斷，以免 if(set()) 這類誤讀。
026、回傳錯誤碼會強迫每一層立刻解碼並污染快樂路徑，失敗應以例外跳出正常敘事。
027、try/catch 本身構成一件事，應整塊抽成函式，讓錯誤策略與業務步驟不要纏在同一層。
028、結構化程式在極短函式中允許提早 return，前提是多出口讓路徑比單旗標迴圈更清楚。
029、能靠抽出函式、具名變數表達的意圖，就不該再寫註解；註解補不了壞結構。
030、值得保留的註解只有法律聲明、非顯見意圖、後果警告、TODO 與公開 API 契約。
031、把程式再講一遍的註解會在下一次修改時變成謊言，因為註解不會被編譯器強制同步。
032、被註解掉的死碼必須刪除，歷史屬於版本控制；留下的區塊會嚇阻後人清理週邊。
033、強制每個方法寫 Javadoc 會製造噪音，非公開程式的樣板標頭應省略而不是填空。
034、右括號註解與分隔線路標代表函式或檔案過長，正確回應是拆分而不是加地標。
035、垂直格式採報紙隱喻，檔案開頭放高階概念與公開政策，私有細節沉到下方。
036、有概念親和性的程式應垂直靠近，呼叫者與被呼叫者的距離要短到能同屏讀完關係。
037、空行只分隔概念區塊，緊密相關的陳述之間保持垂直密度，避免被空白拆散思緒。
038、水平格式用縮排表達巢狀深度；為對齊等號而插入空白對理解幫助有限且污染 diff。
039、同一團隊同一風格，格式是群體契約，個人偏好不得在同一模組留下互相覆蓋的空白戰爭。
040、物件隱藏資料並暴露行為；資料結構暴露資料且幾乎沒有行為，兩者在擴充方向上反對稱。
041、穩定函式集合、常新增型別時用物件多型；穩定型別集合、常新增操作時用資料結構加程序。
042、Law of Demeter 禁止透過回傳物件再往下探內部，a.getB().getC() 這種 train wreck 是耦合指標。
043、半物件半資料結構的 hybrid 最糟，既破壞封裝又把行為趕出型別，呼叫端兩邊都得不到好處。
044、DTO 只負責過邊界載資料；Active Record 若再塞領域規則，資料庫對應與業務變更會互相綁死。
045、資料抽象的檢驗是能否替換內部表示而不迫使呼叫端改寫，一堆 getter 並不構成抽象。
046、例外讓快樂路徑連續可讀，finally 則保證無論成功或失敗都執行釋放。
047、先寫 try-catch-finally 再填主體，等於先釘死失敗時的狀態契約再實作成功路徑。
048、未檢例外避免為了遠端失敗而在中間層亂加 throws，檢核例外常把實作細節洩漏成簽章。
049、丟出時必須附帶失敗操作與當時狀態，catch 端才不必反向拼湊 log 上下文。
050、例外類型依呼叫端需要的處理策略分組，而不是依拋出端套件或底層來源分組。
051、回傳 null 把空值檢查複製到每一個呼叫點，漏一處就是 NPE，應改特例物件或例外。
052、公開 API 不應接受 null 引數把契約變成雙軌，非法輸入應在邊界直接拒絕。
053、第三方型別用 adapter 包在邊界，Map 或廠商類不得滲進領域核心成為到處出現的語彙。
054、Learning test 把第三方行為鎖成可執行規格，升級版本時先跑邊界測試定位破壞點。
055、TDD 三定律依序為先寫失敗測試、只寫剛好通過的產品碼、再消除重複，三者循環不可跳步。
056、測試碼與產品碼同一清潔標準，髒測試會變慢、變脆、被丟棄，等於拆掉重構的安全網。
057、FIRST 要求測試必須快、彼此獨立、可在任何環境重複、以布林結果自驗證、及時寫於產品碼之前或緊接其後。
058、一個測試只驗證一個概念，多個 assert 可以存在，但不可把無關行為綁成一次全倒的套件。
059、Build-Operate-Check 把整備、操作、斷言分成三段，測試讀起來才像行為規格而不是腳本垃圾場。
060、類的大小以職責數目衡量，兩個以上獨立變更理由就該拆，行數不是主要尺。
061、SRP 的變更理由對應不同利害關係人，檔案還有空白並不構成繼續塞規則的正當性。
062、高內聚表示多數欄位被多數方法使用；為恢復內聚而抽出的小類是設計收斂，不是隨意碎片。
063、對擴充開放、對修改封閉，把易變政策隔在多型或策略邊界後，穩定客戶端才不必隨規則改編譯。
064、系統組裝與系統使用分離，new 與生命週期留在 main 或容器，業務物件只接收已注入的抽象。
065、Dependency Injection 讓測試能塞入 test double，生產組裝則在邊界一次接線，兩者共用同一套建構政策。
066、日誌、交易、安全這類橫切關注用 proxy 或 aspect 掛上，避免污染領域方法的簽章與抽象層。
067、架構決策延到有真實約束再下，過早的大型抽象會變成錯誤骨架，後續只能繞過它寫髒碼。
068、簡單設計四規依優先序為測試全綠、沒有重複、表達意圖、最少類與方法，後面不得犧牲前面。
069、消除重複會逼出 TEMPLATE METHOD 或 STRATEGY，抽象是重構的結果，不是一開始畫的類圖。
070、並發把做什麼與何時做解耦，但共享可變狀態會讓單執行緒直覺全部失效。
071、並發程式必須與其他邏輯隔離，縮小共享範圍，能傳不可變複本就不要讓執行緒共用可變物件。
072、先辨識 producer-consumer、readers-writers 或 dining philosophers，再選擇鎖、佇列或不可變資料，而不是先加 synchronized。
073、synchronized 區段必須極短，執行緒與連線必須有上界，關閉路徑必須能收斂，否則掛起會看起來像隨機失敗。
074、條件應封裝成具名布林函式，魔術數字應成具名常數，負向條件應改寫成正向，讓分支讀成政策而非位元運算。
075、邊界條件集中在一處、時間耦合必須在名稱或簽章上顯性化、可設定資料留在高階，避免呼叫鏈上的傳遞導航。
